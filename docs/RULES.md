# Формат и применение правил

## Назначение базы

База правил хранится отдельно от плана в `data/rules.json`. Исходный демонстрационный набор находится в `data/demo_rules.json`. Его шесть правил синтетические. Их числа используются для проверки алгоритма и не являются действующими строительными нормативами.

Корневой объект содержит `schema_version: 1` и список `rules`. В базе допускается не более 150 правил. Идентификаторы правил должны быть уникальными.

## Структура правила

| Поле | Содержание |
|---|---|
| `id`, `title` | Идентификатор и название |
| `types_a`, `types_b` | Типы первого и второго объекта |
| `parameter` | Проверяемый параметр |
| `operator` | Оператор сравнения |
| `value`, `unit` | Число и единица при наличии |
| `scope` | Область применения по принадлежности участкам |
| `conditions`, `exceptions` | Структурированные условия и исключения |
| `conditions_text`, `exceptions_text` | Текст условий и исключений |
| `unresolved` | Неразобранные положения |
| `original_fragment` | Исходная цитата |
| `source` | Вид, название, редакция, пункт, ссылка и отметка проверки источника |
| `status`, `enabled` | Статус просмотра и активность |

Число или единица могут отсутствовать у кандидата. Для активации числового правила они обязательны. Числа должны быть конечными. Допустимый диапазон `value` — от 0 до 1 000 000.

Статусы просмотра: `draft`, `needs_review`, `confirmed`, `rejected`. Вычислитель использует правила с `status: confirmed` и `enabled: true`. Остальные записи сохраняются в базе, но не участвуют в проверке плана.

## Типы и параметры

| Код | Тип объекта |
|---|---|
| `house` | Дом |
| `garage` | Гараж |
| `bathhouse` | Баня |
| `outbuilding` | Хозяйственная постройка |
| `septic` | Септик |
| `cesspit` | Выгребная яма |
| `well` | Колодец |
| `bed` | Грядка |
| `greenhouse` | Теплица |
| `shrub` | Куст |
| `tree` | Дерево |

`boundary` обозначает границу назначенного участка. Неизвестные типы сохраняются в кандидате, но препятствуют активации.

| Параметр | Значение |
|---|---|
| `distance` | Минимальная дистанция заполненных контуров a и b |
| `boundary_distance` | Отступ контура a от границы его участка; `types_b: ["boundary"]` |
| `height_m` | Физическая высота a из `attributes.height_m`; `types_b: []` |

Поддерживаемые операторы: `>=`, `>`, `<=`, `<`, `==`, `!=`. Единицы `m`, `cm`, `mm` и `м`, `см`, `мм` приводятся к метрам.

Области `scope`: `any`, `same_parcel`, `different_parcels`, `adjacent_parcels`. Для последней проверяется нулевая дистанция между границами разных участков. Такая проверка включает касание и пересечение; она не устанавливает кадастровое соседство.

## Условия и исключения

Условия имеют вид:

```json
{"target": "a", "field": "material", "operator": "==", "value": "wood"}
```

`target` задаёт роль a или b. `field` указывает характеристику объекта. `value` является строкой, числом или логическим значением. Примеры характеристик: `material`, `height_m`, `watertight`, `tree_class`.

Все элементы `conditions` соединяются оператором «И». Элементы `exceptions` соединяются оператором «ИЛИ». Ложное условие или истинное исключение делает правило неприменимым. Если применимость нельзя определить из-за отсутствующего или несовместимого значения, результат — `insufficient_data`.

Для сравнения чисел логические значения не используются как 0 и 1. Условия роли b допускаются только для правила с двумя объектами. Текстовое условие без структурированной формы, текстовое исключение без структурированной формы и непустой `unresolved` препятствуют активации.

## Синтетический пример

Ниже приведён кандидат учебного правила. Значение 2 м не является нормативным.

```json
{
  "id": "synthetic_garage_setback",
  "title": "Учебный отступ гаража",
  "types_a": ["garage"],
  "types_b": ["boundary"],
  "parameter": "boundary_distance",
  "operator": ">=",
  "value": 2,
  "unit": "m",
  "scope": "any",
  "conditions": [],
  "exceptions": [],
  "conditions_text": "",
  "exceptions_text": "",
  "unresolved": [],
  "original_fragment": "Синтетический пример: расстояние от гаража до границы участка должно быть не менее 2 м.",
  "source": {
    "kind": "educational",
    "title": "Синтетический учебный текст",
    "edition": "1",
    "clause": "пример",
    "url": "",
    "verified": false
  },
  "status": "draft",
  "enabled": false
}
```

## Источник и активация

Поле `source.kind` принимает `educational`, `normative` или `unknown`. Источник `unknown` не допускается для активного правила.

Для нормативного правила требуются `title`, `edition`, `clause`, `url` и `verified: true`. Пользователь должен сверить цитату, редакцию, пункт и условия применения с документом. Сервер проверяет наличие метаданных и отметку подтверждения. Достоверность ссылки, содержание документа и его актуальность сервер не устанавливает.

На вкладке «База правил» пользователь редактирует JSON и подтверждает просмотр. Маршрут подтверждения проверяет поддерживаемую структуру и отношения с активной базой. Доказанный дубль или конфликт блокирует запись. Совпадающий ID обновляет запись, а новый ID добавляет её. Импорт заменяет всю базу.

## Результат проверки размещения

| Статус | Условие |
|---|---|
| `violation` | Применимое требование не выполнено |
| `complies` | Применимое требование выполнено |
| `insufficient_data` | Недостаточно сведений для вычисления или определения применимости |

Результат включает объекты, фактическое и требуемое значение, оператор, единицы, условия, объяснение, источник и точки кратчайшего отрезка. Неприменимые правила не включаются в результаты.

Геометрические проверки выполняются отдельно. Выход за назначенный участок даёт нарушение. Пересечение, вложение или касание объектов отображается как геометрическое предупреждение. Допустимость совмещения по назначению объектов проверяется пользователем.

Алгоритм сравнения кандидатов описан в [NEURAL_METHOD.md](NEURAL_METHOD.md#сравнение-правил). HTTP-операции базы описаны в [API.md](API.md).
