# HTTP API

## Подключение

При стандартном запуске базовый адрес — `http://127.0.0.1:8000`. Запросы и ответы используют JSON. Для POST-запросов указывается `Content-Type: application/json`.

Интерактивная спецификация доступна по адресу `http://127.0.0.1:8000/docs`, схема OpenAPI — `http://127.0.0.1:8000/openapi.json`.

## Маршруты

| Метод и путь | Входные данные | Назначение |
|---|---|---|
| `GET /api/health` | Нет | Статус сервера и версия |
| `GET /api/example` | Нет | Пример плана |
| `POST /api/plan/validate` | План | Проверка и нормализация формата |
| `POST /api/measure` | План и конечные точки a/b | Дистанция и кратчайший отрезок |
| `POST /api/check` | План и необязательная база правил | Геометрия и активные правила |
| `GET /api/rules` | Нет | Текущая база |
| `POST /api/rules/relations` | База правил | Отношения между правилами без записи |
| `POST /api/rules/confirm` | Одно правило | Проверка, подтверждение и включение |
| `POST /api/rules/import` | База правил | Замена базы после проверки |
| `GET /api/ai/status` | Необязательный параметр `model` | Доступность сервиса и выбранной модели |
| `POST /api/ai/analyze` | Текст, источник, модель и параметры | Извлечение кандидатов |
| `GET /api/dataset` | Нет | Синтетический корпус и эталоны |

План описан в [ARCHITECTURE.md](ARCHITECTURE.md). База правил описана в [RULES.md](RULES.md). Формат анализа и параметры описаны в [NEURAL_METHOD.md](NEURAL_METHOD.md).

## Измерение

Тело запроса содержит `plan`, `a`, `b`. Каждая конечная точка имеет один из видов:

```json
{"kind": "point", "point": {"x": 3, "y": 4}}
```

```json
{"kind": "object", "id": "home"}
```

```json
{"kind": "boundary", "id": "own"}
```

Идентификаторы должны существовать в переданном плане. Ответ содержит `distance`, `unit: "м"` и `points` из двух пар координат. Число округляется до четырёх знаков после запятой.

## Проверка плана

Тело `POST /api/check` содержит `plan` и необязательное поле `rules`. Если база не передана, используется `data/rules.json`.

Ответ содержит `results`, счётчики `counts` по трём статусам и `checked_rules`. Геометрические проверки выполняются независимо от числа активных правил. Числа в счётчиках относятся к результатам проверок, а не к количеству уникальных объектов.

## Операции базы

Подтверждение принудительно задаёт `status: confirmed` и `enabled: true`. Правило с существующим ID заменяет соответствующую запись. Остальные записи сохраняются. Дубли и конфликты проверяются относительно активной базы.

Импорт принимает объект `schema_version`/`rules` и заменяет текущую базу. Активные импортируемые правила должны иметь статус подтверждения, поддерживаемую структуру и необходимые метаданные источника.

## Анализ текста

Ответ успешного анализа содержит `candidates`, `fragments`, `entities`, `relations`, `trace`, `run` и сообщение о необходимости просмотра. Кандидаты возвращаются неактивными. Запрос анализа не изменяет базу правил.

Доступность модели определяется по списку моделей Ollama. Этот статус не подтверждает успешность извлечения или его качество. Ошибки последующего вызова возвращаются отдельно.

## Ошибки

| HTTP-код | Причина |
|---|---|
| 400 | Недопустимое имя локального сервера в заголовке Host |
| 403 | POST-запрос с несовпадающим Origin |
| 413 | Content-Length превышает 2 000 000 байт |
| 422 | Неверный формат, геометрия, ссылки или условия активации |
| 409 | Дубли или противоречия препятствуют изменению базы |
| 503 | Ollama или выбранная модель недоступны |
| 502 | Ответ модели не прошёл проверку |

Поле `detail` содержит описание ошибки. При ошибке схемы дополнительно возвращается `errors`. При конфликте базы возвращается `relations`. Для ошибок анализа поле `code` имеет значение `model_unavailable` или `invalid_model_response`.
